# DESIGN

## [ALTERNATIVES_CONSIDERED]

### 대안 A: 각 웹 페이지(models.js, ollama-test.js)에 각각 독립된 매핑 및 필터 연산 로직을 작성하는 방식
- **장점**: 페이지별로 필요한 최소한의 필터링 조건만 부분 구현하므로 초반 구현이 직관적입니다.
- **단점**:
  - 모델 아키텍처 분류 규칙(`getFamily`)이나 필터 판단 연산이 두 JS 파일 간에 이중 작성되어 **코드 중복**이 발생합니다.
  - 향후 새로운 모델 패밀리를 추가하거나 필터 룰을 수정할 때, 양측 소스 코드를 동일하게 복사-붙여넣기 해야 하므로 **유지보수 정렬이 완전히 무너집니다.**

### 대안 B: [선택안] 공통 자바스크립트 유틸리티 (`admin-common.js`)에 데이터 처리 및 필터 핵심 로직을 완전히 일원화 및 공통 모듈화하는 방식
- **장점**:
  1. **SSOT (Single Source of Truth) 확립**: 모델명 정제, 실제 패밀리 판별(`getFamily`), 그리고 다차원 필터링 연산(`filterModels`)을 `admin-common.js`에 공통 유틸리티로 완전 격리하여 단 한 곳에서 관리합니다.
  2. **재사용성 극대화**: `admin-common.js`는 이미 모든 어드민 페이지(`base.html`에 명시)에 기본 임포트되어 있으므로, `models.js`와 `ollama-test.js`가 추가 의존성이나 결합도 없이 동일한 데이터 정제 API를 깔끔하게 호출해 쓸 수 있습니다.
  3. **유지보수 용이성**: 추후 새로운 아키텍처 패밀리나 필터 옵션(예: 양자화 필터 등)이 추가되더라도 공통 파일 한 곳만 수정하면 전체 서비스에 즉시 동시 적용됩니다.

---

## [SOLUTION]

### 1. 공통 데이터 처리 아키텍처 설계 (`admin-common.js` 확장)
공통 네임스페이스 영역에 설치 모델 분석 및 실시간 필터 연산을 수행하는 범용 함수군을 설계합니다.

- **`window.getActualFamily(m)`**:
  - 모델명(`m.name`)에 `hf.co/` 경로가 섞인 경우 이를 완벽히 파싱 및 정제하여 실제 파일명에 근거한 키워드를 뽑아내고, 이를 아키텍처 매핑 정규식 리스트와 대조해 순수 패밀리명(예: `gemma3`, `gemma3n`, `gemma4`, `deepseek-r1`, `granite4`, `ministral-3`, `qwen3`, `qwen3-vl`, `qwen3.5`, `hyperclovax`, `kanana`, `llava` 등)으로 완전 분류합니다.
  - hf 모델이 아닌 일반 Ollama 공식 모델도 이 룰을 통과시켜 동일 가중치 그룹으로 묶습니다.
- **`window.parseParameterSize(paramStr)`**:
  - `"4.3B"`, `"1.5B"`, `"270M"` 등 문자열 파라미터 규격을 실수형 수치(B 단위 기준)로 변환해 크기 연산이 가능하게 합니다.
- **`window.filterModelList(models, filters)`**:
  - 입력값: `models` (설치 모델 리스트), `filters` (검색어, 파라미터 범위, 용량 상한값, 모델 유형, 다운로드 출처)
  - 출력값: 모든 필터 조건을 통과하여 가시적으로 렌더링될 대상 모델 리스트

### 2. 모델 관리 페이지 UI/UX 설계 (`models.html` / `models.js`)
- **UI 구성**: "설치된 모델" 카드 내부 테이블 상단에 세련된 가로 정렬 필터바를 전격 장착합니다.
  - 검색창, 파라미터 필터 셀렉트, 파일 용량 제한 range 슬라이더 바, 모델 유형 셀렉트, 출처 셀렉트
- **그룹화 렌더링**: 기존의 밋밋한 1차원 테이블 구조 대신, 공통 `getActualFamily` 유틸을 적용해 **아키텍처 패밀리별 카드 또는 행 그룹 헤더를 미려하게 삽입**하여 어떤 아키텍처 그룹에 속해 있는지 한눈에 보기 편하도록 가독성을 개편합니다.

### 3. Ollama 테스트 페이지 UI/UX 설계 (`ollama-test.html` / `ollama-test.js`)
- **UI 구성**: 기존 "모델 선택" 필드와 체크박스 목록 상단에 동일한 레이아웃의 공통 필터바(슬라이더 포함)를 미려하게 추가합니다.
- **상태 보존 가드**: 사용자가 모델들을 체크해둔 선택 상태(State)는 내부 메모리에 안전하게 유지하며, 필터가 조작되어 목록이 변경되더라도 **기존 선택 상태가 소멸되지 않도록 렌더링 독립성**을 완전 보증합니다.
- **가시 범위 일괄 조작**: "전체 선택" 및 "전체 해제" 버튼 클릭 시, 화면 뒤에 가려진 모델까지 휩쓸려 오작동하지 않고 **현재 필터를 통과하여 "화면에 선명하게 노출되어 있는 모델들"만 지능적으로 일괄 체크/해제**되도록 로직을 세분화합니다.

## [REVIEW_LOG]
* **검토자**: Reviewer Persona
* **검토 의견**:
  - **Critical Design Flaw 1 (클라이언트 연산 최적화)**: 모델 리스트가 50개 이상 많아진 상태에서 사용자가 용량 슬라이더를 연속으로 빠르게 조작(드래그)할 경우, 매 이벤트마다 필터 및 그룹화 루프 연산이 돌고 전체 DOM을 렌더링하면서 극심한 화면 버벅임(UI Lag)이나 끊김 현상이 발생할 수 있습니다. 이를 완벽히 방지하기 위해, range 슬라이더 조작 시 **Debounce(최소 50~100ms) 기법을 부착하여 드래그 조작이 멈추거나 잦아드는 시점에 최종 렌더링이 가동**되도록 지연 연산 처리를 필수로 적용해야 합니다.
  - **가시성 바인딩 정밀성**: 렌더링 시 테이블 행이나 체크박스 카드를 매번 비우고 완전히 새로 그리는 대신, 혹은 필터링되지 않은 것들을 `hidden` 클래스로 단순히 제어할 때의 레이아웃 무너짐을 검토해야 합니다. 패밀리 그룹화 헤딩 영역의 경우 하위 모델이 전부 필터링되어 보이지 않을 때 **패밀리 헤더 타이틀만 홀로 흉하게 남아 있지 않도록, 헤더 영역까지 지능적으로 숨김(`hidden`) 처리**하는 고도의 렌더링 트래킹 로직이 요구됩니다.
