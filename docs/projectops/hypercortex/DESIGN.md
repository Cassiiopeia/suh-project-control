# DESIGN

## [ALTERNATIVES_CONSIDERED]

### 대안 A: 단순 다중 선택 Select박스 및 기존 카드 나열형 구조
- **장점**: 개발 공수가 가장 적음. 기존 HTML과 JS의 골격을 거의 그대로 유지하고 select에 `multiple` 속성만 추가하여 요청을 루프로 돌리면 됨.
- **단점**: 설치된 모델이 20~30개가 넘어갈 경우 다중 선택이 극도로 불편함. 결과가 단순 카드 목록으로 아래로 길게 나열되므로 어떤 모델이 어떤 스키마 제약에서 우수한 성능(토큰 처리 속도, 로드 딜연 등)을 보였는지 한눈에 종적 비교가 불가능함.

### 대안 B: 패밀리 기반 다중 체크박스 UI + 요약 비교 테이블 및 상세 토큰 지표 카드 (추천안)
- **장점**:
  1. `models.html`의 직관적인 패밀리별 카드 정렬 UI를 이식하여 설치된 여러 모델을 계열별(gemma3, qwen3, deepseek 등)로 한눈에 보며 쉽게 다중 선택할 수 있음.
  2. 실행 시 선택된 모델들의 테스트를 순차적으로 직렬화(Serialization)하여 서버 메모리 안전성을 보장하고 프로그레스 바로 상태를 시각화함.
  3. 결과 출력 시 각 모델의 출력을 세부 성능 지표(총 소요 시간, 모델 로드 시간, 추론 속도, 입력/출력 토큰 정보)와 함께 일목요연하게 정리한 **'배치 테스트 요약 테이블'**을 실시간으로 그려주고, 하단에는 상세 JSON 응답 구조를 보여주는 전용 카드를 배치하여 정밀 분석과 종적 비교가 모두 가능해짐.
- **단점**: UI 마크업 구성과 자바스크립트의 결과 렌더링 로직 개편을 위한 초기 설계 및 코드 수정 범위가 다소 증가함.

## [SOLUTION]

### 1. UI/UX 구성 설계 (ollama-test.html 개편)
- **요청 구성 (Request Configuration) 카드**:
  - **모델 선택 영역**: 단일 드롭다운 대신 **"모델 선택" 필드셋**을 만들고, `models.html`과 같은 형태로 패밀리별 타이틀(gemma3, exaone, HuggingFace 등) 밑에 체크박스와 `vision`/`size` 배지가 부착된 그리드 형태로 구성합니다.
  - **전체 선택 / 전체 해제** 편의 버튼을 최상단에 배치합니다.
  - **기타 파라미터**: temperature, format 모드(none/json/schema), 시스템 프롬프트, 유저 프롬프트, JSON Schema 편집기는 기존 UI 구조를 세련되게 정돈하여 계승합니다.
- **실행 및 진행 상황 (Progress Feed) 영역**:
  - 실행 버튼 클릭 시 비활성화 상태가 되며, 전체 선택된 모델 개수 중 현재 몇 번째 모델을 테스트하고 있는지 알려주는 **"진행상황 인디케이터(Progress Bar 및 텍스트)"**를 표시합니다.
- **테스트 요약 비교 테이블 (Comparison Table) 카드 (신설)**:
  - 이번 실행(Run) 결과를 일목요연하게 비교할 수 있는 요약 표를 동적으로 생성합니다.
  - **컬럼 구성**: 모델명 | 상태 | 총 시간 | 로드 지연 | 추론 시간 | 입력 토큰 | 출력 토큰 | 출력 속도 (tok/s) | Schema 준수 여부
- **상세 결과 카드 (Detailed Cards) 목록**:
  - 기존의 결과 리스트 형식을 고도화하여, 각 카드 내부에서 모든 토큰 관련 메트릭을 정교하게 시각화(배지 혹은 테이블 형태)하고, JSON 구조를 보기 쉽게 포맷팅된 코드 블록으로 표현합니다.

### 2. 컴포넌트 데이터 흐름 및 로직 설계 (ollama-test.js 개편)
- **모델 목록 로딩 및 렌더링**:
  - `loadModels()`가 완료되면 `groupByFamily` 함수를 거쳐 계열별 카테고리를 만들고 동적으로 체크박스 형태로 화면에 추가합니다.
- **비동기 순차 실행 루프**:
  ```javascript
  for (const model of selectedModels) {
    // 1. UI 진행도 업데이트 (X/Y 진행 중)
    // 2. API 호출: POST ../ollama/chat
    // 3. 응답 메트릭 가공 및 요약 테이블 행(row) 추가
    // 4. 상세 결과 카드 추가
    // 5. 메모리 안정화를 위한 슬립 대기 (300ms)
  }
  ```
- **상세 메트릭 계산 및 스키마 검증**:
  - `prompt_eval_count` (입력 토큰 수), `eval_count` (출력 토큰 수), `load_duration_ms` (모델 로딩), `eval_duration_ms` (추론 시간), `tokens_per_second` 등을 배지와 테이블로 완벽 대응합니다.
  - **클라이언트 측 JSON Schema 자체 검증**: 반환된 JSON 텍스트를 파싱하여, 스키마의 `required` 필드가 JSON 내에 모두 정의되어 있는지, 배열/객체 형태에 오류가 없는지 가볍게 분석하여 검증 마크(성공/경고/실패)를 띄웁니다.

## [REVIEW_LOG]
* **검토자**: Reviewer Persona
* **검토 의견**:
  - **디자인 결함 분석**: 요약 비교 테이블이 추가될 때, 여러 번 "실행"을 클릭하면 테이블이 누적될지, 아니면 새로운 런이 실행될 때마다 테이블이 리셋될지에 대한 명확한 상태 관리가 필요합니다.
  - **해결 방안**: 한 번의 '실행' 버튼 클릭 시 단일 "배치 세션(Batch Session)" ID를 생성하고, 해당 세션에 대한 요약 테이블을 결과 리스트의 머리에 새로 삽입해 주는 것이 가장 이상적입니다. 즉, "실행"할 때마다 상단에 **[배치 요약 테이블 + 개별 상세 카드 그룹]**이 한 세트로 추가되도록 설계하면 여러 차례의 프롬프트 실험 역사를 완벽하게 보존하면서도 직관적으로 비교할 수 있습니다.
  - **i18n & a11y 표준 준수**: 동적으로 생성되는 모든 체크박스는 적절한 `<label>` 태그와 `aria-label`을 지정하여 웹 접근성을 보장해야 합니다.
