# REQUIREMENT

## [PROBLEM]
현재 제공되는 Ollama Structured Output 테스트 페이지(`ollama-test.html`, `ollama-test.js`)는 다음과 같은 한계가 존재하여 사용자(개발자/관리자)가 여러 AI 모델의 JSON Schema 지원 및 성능 품질을 정교하게 비교·분석하기 어렵습니다.
1. **단일 모델 선택 제약**: 한 번에 단 하나의 모델만 드롭다운에서 선택하여 실행할 수 있어, 동일한 프롬프트와 JSON Schema에 대해 여러 모델의 구조화 출력 성능을 즉각적으로 비교할 수 없습니다.
2. **부족한 성능 메트릭 시각화**: `OllamaService`는 내부적으로 토큰 수, 로드 시간, 생성 시간, 초당 토큰 수(`tokens_per_second`) 등의 상세 메트릭을 응답하고 있으나, 테스트 페이지의 결과 카드에서는 단순히 전체 시간(`total_duration_ms`)과 초당 토큰 수만 표시되고 있어 입출력 토큰 규모나 세부 로드/생성 지연을 비교 분석하기 어렵습니다.
3. **불편한 모델 선택 UI**: 설치된 모델이 많아질 경우 단일 드롭다운 목록에서 특정 모델을 하나씩 찾아 선택하는 방식이 매우 비효율적입니다. `models.html` 페이지와 유사하게 계열(Family)별로 묶이고 `vision` 등의 태그 정보가 직관적으로 제공되는 모델 다중 선택 UI가 요구됩니다.

## [REQUIREMENT]
1. **모델 다중 선택 UI 도입 (Multi-Model Selection)**
   - `models.html`의 패밀리 그룹핑(Family grouping) 방식을 참고하여, 설치된 모델들을 계열별로 시각적으로 분류하여 체크박스로 다중 선택할 수 있도록 개선합니다.
   - Vision 태그(모델 옆에 표시) 및 크기 정보를 제공하여 모델의 제원을 쉽게 식별할 수 있어야 합니다.
   - 전체 선택, 전체 해제와 같은 편의 기능이 제공되어야 합니다.
2. **순차적 벤치마크 실행 흐름 (Sequential Evaluation)**
   - 선택된 여러 모델에 대해 사용자가 입력한 프롬프트, 온도(temperature), 포맷 옵션(JSON Schema 포함)을 활용해 순차적으로 `/ollama/chat` 테스트를 실행합니다.
   - 순차 실행을 수행하여 다중 모델 로드로 인한 서버 리소스 폭주(OOM 등)를 방지합니다.
   - 현재 실행 중인 모델과 남은 실행 진행 상황을 사용자에게 명확히 피드백(프로그레스 바 혹은 텍스트 스피너)합니다.
3. **상세한 성능 및 토큰 메트릭 테이블/카드 제공 (Detailed Performance Metrics)**
   - 결과 카드 및 비교 정보에 다음 지표들을 명확하게 추가 표기합니다:
     - **총 응답 시간 (Total Time)**: 전체 처리 시간
     - **모델 로드 지연 (Load Time)**: `load_duration_ms`
     - **생성 시간 (Generation Time)**: `eval_duration_ms`
     - **입력 토큰 수 (Prompt Tokens)**: `prompt_eval_count`
     - **출력 토큰 수 (Output Tokens)**: `eval_count`
     - **출력 속도 (Tokens per Second)**: `tokens_per_second` (tok/s)
   - 각 모델의 생성 결과가 유효한 JSON 인지 여부(JSON Schema 유효성)를 파싱 및 형식을 맞춰 포맷하여 강조 표시합니다.
4. **결과 비교 편의성 향상**
   - 단일 실행 결과들의 단순 누적 목록뿐만 아니라, 동일 실행(같은 프롬프트 및 스키마에 대한 배치 테스트)에 대해 각 모델의 결과와 지표를 **한눈에 나란히 비교할 수 있는 표(Table) 또는 카드 기반 레이아웃**을 제공합니다.
   - 단일 모델만 선택했을 경우와 다중 모델을 선택했을 경우 모두 자연스럽게 아우르는 직관적이고 미려한 UI/UX를 제공합니다.

## [ASSUMPTIONS]
- Ollama 서버가 로컬에서 구동 중이며, `/ollama/chat` API를 통해 반환되는 `metrics` 객체 내의 데이터(`prompt_eval_count`, `eval_count`, `eval_duration_ms` 등)가 안정적으로 로드된다고 가정합니다.
- 동시 처리가 아닌 순차 처리를 진행하므로, 클라이언트 사이드에서 `for...of` 비동기 루프를 사용하여 요청을 직렬화하여 수행합니다.

## [AMBIGUITY]
- **비교 분석 결과의 누적 방식**: 사용자가 "실행"을 누를 때마다 이전 배치 실행 결과가 유지되어야 하는가, 아니면 한 번의 테스트 런(Run) 단위로 완결하여 결과를 갱신 및 관리할 것인가?
  - *해결 방안*: 기존에 구현된 '전체 지우기'와 개별 카드 추가 방식을 활용하되, 동일 런(Batch Run)으로 묶인 결과들을 식별할 수 있는 그룹화 카드나 비교 테이블을 상단 혹은 별도 탭에 두는 것이 편리할 것입니다.

## [REVIEW_LOG]
* **검토자**: Reviewer Persona
* **검토 의견**:
  - **Critical Edge Case 1 (OOM & Timeout 리스크)**: 다중 모델을 연속적으로 호출하는 과정에서 이전 모델이 메모리(VRAM)에서 언로드(Unload)되지 않은 상태로 다음 대형 모델이 로드되면 서버 VRAM 부족으로 크래시가 나거나 비정상 응답이 올 수 있습니다. 순차 루프 사이사이에 잠시 딜레이를 주거나 실패 시 우아하게 넘어가는 예외 처리가 자바스크립트 수준에서 확실히 보장되어야 합니다.
  - **Critical Edge Case 2 (JSON Schema 검증 무결성)**: 모델이 반환하는 결과가 유효한 JSON인지를 체크하는 것을 넘어, 사용자가 설정한 **JSON Schema의 명세와 실제 반환된 JSON 인스턴스가 완벽히 부합하는지**를 검증(Validation)해주는 클라이언트 로직이 있으면 벤치마크의 신뢰도가 극대화될 것입니다. (단순 파싱 성공 여부만으로는 스키마 준수 여부를 알 수 없음)
  - **i18n & UI 확장성**: UI 개선 시 하드코딩된 한글 메시지 대신 다국어 지원에 대응할 수 있도록 레이블 구성 방식에 유의하십시오.
